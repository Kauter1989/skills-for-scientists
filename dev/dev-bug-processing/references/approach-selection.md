# Выбор подхода к обработке дефектов

Нормативный документ `dev-bug-processing`. Определяет профиль репозитория и
подход, который наследует сгенерированный `dev-bug-process`.

## 1. Профиль репозитория

| Вопрос | Варианты | Зачем |
|---|---|---|
| Стек | python / javascript / typescript / java / go / rust / other | команды и пути к тестам |
| Тестовый фреймворк | pytest / unittest / jest / vitest / junit / go test / cargo test / other | форма red test |
| Команда тестов | любая | воспроизведение и проверка |
| Путь к тестам | `tests/`, `src/test/java/`, `./...` | место red test |
| Трекер | github / jira / none | формат issue и ссылки |
| Окружение | local / container / production / benchmark | стратегия воспроизведения |
| Команда | small / enterprise | глубина церемонии |
| Compliance | none / audit | evidence и approvals |
| Политика флейков | strict / retry | порог прогонов |
| Глубина | light / standard / deep | набор проверок |
| Approval | user / autonomous | кто утверждает план |

## 2. Матрица

| Профиль | Подход | Что добавляет |
|---|---|---|
| Локальный тестовый фреймворк, обычные дефекты | `test-first` | red test, минимальный вход, `git bisect` |
| Зависимость от окружения или сервисов | `container-first` | закреплённый образ, compose, детерминированные данные |
| Production-инцидент | `incident-first` | timeline, логи и трейсы, rollback, затем локальное воспроизведение |
| Много дефектов или исследовательский стенд | `benchmark-first` | пакетная обработка, метаданные, сравнение ревизий |
| Малая команда, простой процесс | `lightweight` | минимальный отчёт без тяжёлого трекера |

Правила выбора:

1. Явно указанный подход имеет приоритет, если он входит в список.
2. `production` или `incident` → `incident-first`.
3. `benchmark` или `research` → `benchmark-first`.
4. `container` или `docker` → `container-first`.
5. `team=small`, `compliance=none`, `repro_depth=light` → `lightweight`.
6. Иначе → `test-first`.

## 3. Что меняется и что нет

Меняется:

- команда запуска тестов и путь к тестам;
- формат issue и ссылка на трекер;
- наличие контейнера, логов, трейсов и rollback;
- глубина локализации и число прогонов;
- набор шаблонов и примеров.

Не меняется:

1. Подробное описание: expected / actual, окружение, версия, шаги, входы,
   логи.
2. Воспроизводимость: минимум 3 прогона; флейк — отдельный статус.
3. Минимальный вход.
4. Падающий автотест до фикса.
5. Соответствие падения заявленному symptom.
6. Диагноз с evidence, confidence и следующим probe.
7. Запрет фикса до красного гейта.
8. Артефакты в `docs/bugs/<id>/`.
9. Запрет автоматического запуска недоверенных команд.

## 4. Особенности подходов

### `test-first`

- red test пишется в обычном тестовом дереве;
- минимальный вход уменьшается delta debugging или вручную;
- `git bisect` предлагается как следующий probe, но не запускается
  автоматически;
- подходит большинству библиотек и сервисов с быстрыми тестами.

### `container-first`

- образ и диджест фиксируются в отчёте;
- данные и переменные окружения версионируются;
- тест запускается внутри контейнера; локальный запуск без контейнера не
  считается воспроизведением;
- если контейнер не воспроизводит дефект, статус `not-reproduced`, а не
  «исправлено».

### `incident-first`

- сначала timeline, impact, логи и трейсы;
- mitigation и rollback разрешены до red test;
- фикс запрещён до локального воспроизведения и red test;
- после инцидента артефакты остаются в `docs/bugs/<id>/`.

### `benchmark-first`

- один `bug-id` — один набор артефактов;
- ревизии и метаданные фиксируются;
- пакетная обработка не смешивает дефекты;
- сравнение «до / после» обязательно.

### `lightweight`

- можно не заводить issue и не использовать тяжёлый трекер;
- отчёт всё равно содержит expected / actual, окружение и red test;
- 9 инвариантов сохраняются.

## 5. Ошибки выбора

- `test-first` для production-инцидента без локального воспроизведения;
- `container-first` без фиксации образа и данных;
- `incident-first`, который заканчивается hotfix без red test;
- `benchmark-first`, который смешивает несколько дефектов;
- `lightweight`, который отключает воспроизводимость;
- выбор подхода без опроса;
- генерация навыка до `approved`.
