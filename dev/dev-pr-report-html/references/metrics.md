# Метрики отчёта об изменениях

Нормативный документ скилла `dev-pr-report-html`. Определяет, что считается
метрикой, откуда берётся число, как считается и когда оно красное.

Общие правила:

1. Единица измерения называется всегда (`tokens`, `%`, `×`, `на 1000 LOC`).
2. Уровень качества данных (`measured` / `derived` / `estimated`) ставится
   рядом с числом, а не в сноске.
3. Порог задаётся до расчёта. Если порог не задан и нет базы сравнения,
   статус — `unknown`, а не «на глаз».
4. Округление: проценты — до 0,1; токены — до 1000; деньги — до цента.
   Округление не скрывает точность: `~` и диапазон важнее лишних знаков.
5. Сравнение имеет смысл только внутри одного репозитория и одного
   архитектурного контракта.

---

## Уровни качества данных

| Уровень | Значение | Как выглядит на странице |
|---|---|---|
| `measured` | прямо из инструмента: usage провайдера, логи сессии, CI, линтер | число + зелёный бейдж |
| `derived` | вычислено из Git/AST/графа зависимостей по детерминированной формуле | число + синий бейдж |
| `estimated` | восстановлено по косвенным данным по явной формуле | `~` + диапазон + жёлтый бейдж |
| `expert` | суждение ревьюера по чек-листу, без машинной проверки | число + фиолетовый бейдж |
| `missing` | данных нет | «нет данных» + как получить |

`estimated` без диапазона запрещён: оценка без погрешности — это
замаскированное измерение.

## 1. 💰 Feature Token Budget (FTB)

**Вопрос.** Сколько стоила фича в токенах и деньгах, включая исследование,
ошибки и повторные прогоны?

**Единица.** токены; вторично — валюта, токены на 100 LOC, токены на сущность.

**Формула.**

```
FTB = input + output + cache_read + cache_write
FTB_per_100_loc = FTB / (changed_loc / 100)
FTB_per_entity  = FTB / changed_entities
retry_share     = tokens_spent_after_first_green_run / FTB
```

`changed_loc = added + deleted` (не сумма файлов). Если провайдер отдаёт
`total_tokens`, не складывайте его с составляющими — выберите один источник.

**Источники.**

- usage-объекты в экспорте сессии / API-логах / биллинге шлюза;
- счётчики harverness (OpenCode, Claude Code) по `session id`;
- при отсутствии — реконструкция: `токены ≈ 0,75 × слова` для смешанного
  русского/английского текста, отдельно для input и output. Это `estimated`,
  погрешность ±30 %, указывать диапазон.

**Нормировка.** Абсолютный бюджет сравнивается только с бюджетом
аналогичных фич. Полезные отношения:

- `FTB / LOC` — стоимость единицы изменения;
- `FTB / entity` — стоимость одной затронутой сущности;
- `retry_share` — какая доля ушла на переделки; `>0,25` — дорогая обратная
  связь, `>0,5` — процесс не сходится.

**Порог.** Задаётся бюджетом фичи или медианой последних 5–10 фич. Без
базы — `unknown`. Красный: превышение бюджета более чем на 50 % **и**
`retry_share > 0,3`.

**Ловушки.**

- считать только финальную сессию — бюджет занижается в разы;
- складывать cache read и input, если провайдер уже включил cache в input;
- сравнивать фичи разного размера без нормировки;
- выдавать оценку по словам за измерение.

## 2. 🏗 Architecture Drift Score (ADS)

**Вопрос.** Какая доля архитектурных решений в изменении нарушила правила
репозитория?

**Единица.** % (0–100). Дополнительно — число нарушений по severity.

**Предусловие.** Нужен архитектурный контракт. Источники контракта, в
порядке приоритета:

1. `docs/adr/` и решения о границах слоёв;
2. конституция/`CONVENTIONS.md`/`ARCHITECTURE.md`;
3. конфигурация `import-linter`, `dependency-cruiser`, `eslint-plugin-boundaries`,
   `archunit`, правила слоёв в линтере;
4. если ничего нет — скилл фиксирует контракт как **допущение** в разделе
   «Метод» и помечает все нарушения `expert`. Выдавать такие нарушения за
   машинный факт нельзя.

**Единица анализа — решение, а не строка.** Решения:

- новое ребро зависимости между модулями/пакетами/слоями;
- новый модуль, слой или пакет;
- изменение публичного API (экспорт, сигнатура, контракт);
- изменение схемы данных или миграция;
- новая внешняя зависимость;
- новая точка входа (маршрут, команда, джоб);
- новый сквозной механизм (кэш, очередь, ретраи, фоновая задача).

**Формула.**

```
weighted_violations = 5·critical + 3·major + 1·minor
weighted_compliant  = 5·critical_ok + 3·major_ok + 1·minor_ok
ADS = 100 × weighted_violations / (weighted_violations + weighted_compliant)
```

Знаменатель — только архитектурно значимые решения. Строки, тесты и
документация в него не входят, иначе большой рефакторинг «разбавит» нарушения.

**Классификация.**

| Severity | Пример | Вес |
|---|---|---|
| critical | домен импортирует инфраструктуру; цикл между пакетами; новый слой без ADR; обход границы модуля | 5 |
| major | новый публичный API без контракта/тестов; миграция без rollback; дублирование существующей capability; новая зависимость ради одной функции | 3 |
| minor | нарушение соглашения об именовании слоя; неверное размещение файла; локальная копия утилиты | 1 |

**Пороги по умолчанию.**

| ADS | Статус | Смысл |
|---|---|---|
| `< 5 %` | зелёный | изменение следует архитектуре |
| `5–15 %` | жёлтый | локальные отклонения, нужен разбор |
| `> 15 %` | красный | изменение переопределяет архитектуру |
| нет контракта | `unknown` | сначала контракт, потом число |

**Как проверять.** Построить граф импортов изменённых модулей (AST/линтер),
сравнить с разрешёнными рёбрами; каждое нарушение подтвердить файлом и
строкой; проверить, есть ли ADR на новое решение. Отчёт субагента не
принимается без открытия файла.

**Ловушки.**

- считать нарушением любой новый файл;
- путать «непривычно» с «нарушает правило»;
- мерить ADS в репозитории без контракта;
- складывать ADS разных репозиториев;
- забывать про обратное направление: слой, которому дали лишнюю
  зависимость, тоже дрейф.

## 3. 🧠 Cognitive Load Index (CLI)

**Вопрос.** Сколько разных сущностей нужно удержать в голове, чтобы понять
и отревьюить изменение?

**Единица.** безразмерный индекс; `1,0` = типичная фича проекта.

**Сырой вес сущностей.**

| Сущность | Вес |
|---|---|
| модуль/файл исходного кода | 1 |
| пакет/директория-слой | 3 |
| публичная функция/метод/класс | 2 |
| ORM-модель/таблица | 3 |
| миграция | 3 |
| маршрут/точка входа | 2 |
| внешняя зависимость | 2 |
| конфигурационный ключ | 1 |
| тестовый файл | 0,5 |
| документ/ADR | 0,5 |

```
CLI_raw = Σ weight(entity)
blast_radius = число модулей, импортирующих затронутые (1–2 уровня)
CLI = 0,8·CLI_raw + 0,2·blast_radius
CLI_norm = CLI / median(CLI последних 5–10 фич)
```

Blast radius ограничивается двумя уровнями: дальше связь уже не осознаётся
ревьюером, но всё ещё влияет на риск. Если история мала (`<5` фич), вместо
нормировки печатается сырой индекс и `CLI_norm = null`.

**Пороги.**

| CLI_norm | Статус | Смысл |
|---|---|---|
| `< 1,5` | зелёный | сфокусированное изменение |
| `1,5–3,0` | жёлтый | широкое, нужно разбить ревью по слоям |
| `> 3,0` | красный | изменение трудно удержать; дробить или сопровождать картой |

**Ловушки.**

- мерить строки вместо сущностей;
- игнорировать blast radius: маленький диф в центральном модуле дороже
  большого дифа в листе;
- нормировать по одной предыдущей фиче;
- складывать тесты с тем же весом, что и публичный API.

## 4. 🔄 Agent Iteration Rate (AIR)

**Вопрос.** Сколько циклов, провалов и повторов потребовал агент, прежде
чем изменение стало принимаемым?

**Единица.** % провалов; циклы на задачу; максимум повторов.

**Формула.**

```
failure_rate = failed_verifications / verification_attempts
loops_per_task = cycles / accepted_tasks
thrash = max consecutive repeats of the same failing command without a new hypothesis
```

Проверки: тесты, линтер, сборка, миграции, браузерная проверка, ревью.
Повторный запуск той же команды без изменения кода или гипотезы — это
`thrash`, а не новая итерация. Ручные вмешательства (подсказка, откат,
переформулировка задачи) считаются отдельно.

**Пороги.**

| Показатель | Зелёный | Жёлтый | Красный |
|---|---|---|---|
| failure_rate | `<15 %` | `15–30 %` | `>30 %` |
| thrash | `≤1` | `2` | `≥3` |
| loops_per_task | `≤1,5` | `1,5–3` | `>3` |
| manual interventions | `0` | `1` | `≥2` |

Красный по `thrash` перекрывает зелёный по среднему: среднее скрывает
зацикливание.

**Источники.** Логи tool-call'ов, история CI (`gh run list`), журнал
проверок в сессии, таймлайн коммитов. Если есть только CI — считайте
`failure_rate` по запускам, `loops` пометьте `missing`.

**Ловушки.**

- считать успешные проверки только после первого зелёного;
- смешивать провалы окружения (нет сети, нет зависимости) и провалы кода;
- называть циклом каждый вызов инструмента;
- прятать ручные вмешательства в «исследование».

## 5. 👻 Hallucination Risk (HR)

**Вопрос.** Ссылается ли изменение на API, импорты, файлы и команды,
которых не существует?

**Единица.** подтверждённые случаи на 1000 изменённых LOC; вторично —
абсолютное число и severity.

**Формула.**

```
HR = 1000 × Σ(weight × confirmed_cases) / max(changed_loc, 1)
```

| Тип | Вес | Как подтвердить |
|---|---|---|
| `phantom_api` | 5 | символа нет в установленной версии; падение `AttributeError`/`TypeError` |
| `wrong_signature` | 3 | символ есть, аргументы/тип не совпадают; type checker или вызов в тесте |
| `missing_import` | 2 | импорт не резолвится в окружении проекта (`find_spec`, `tsc`, линтер) |
| `stale_reference` | 1 | файл/флаг/команда/ссылка не существует |

**Пороги.**

| HR | Статус |
|---|---|
| `0` | зелёный |
| `>0` при отсутствии `phantom_api` | жёлтый |
| `≥1` подтверждённый `phantom_api` | красный |
| `>1 на 1000 LOC` | красный |

**Процедура проверки.**

1. Собрать все новые импорты и внешние символы из diff.
2. Для Python — `importlib.util.find_spec` в окружении проекта; для
   TypeScript — `tsc --noEmit`/ESLint; для прочих — компилятор/резолвер.
3. Для внутренних символов — AST/`grep` по определению, а не по вызову.
4. Для путей и команд — проверить существование файла/бинаря.
5. Разделить `confirmed` и `unconfirmed`. Внешний пакет, объявленный в
   зависимостях, но не установленный в среде проверки, — `unconfirmed`,
   а не галлюцинация.
6. Каждый подтверждённый случай — с локацией и доказательством.

**Ловушки.**

- считать галлюцинацией опечатку в комментарии;
- проверять импорты в глобальном Python вместо venv проекта;
- путать устаревший API с несуществующим;
- выдавать «вероятно, выдумано» за подтверждённый случай;
- игнорировать сгенерированные файлы, где ссылки валидны по построению.

## 6. 📏 Context Window Utilization (CWU)

**Вопрос.** Насколько полно агент использовал доступный контекст
репозитория, прежде чем менять код?

**Единица.** % покрытия релевантных файлов; % пикового заполнения окна.

**Формула.**

```
relevant = touched modules ∪ their importers (1–2 уровня)
           ∪ tests of touched modules
           ∪ conventions/ADR/architecture contract
CWU_coverage = read_before_first_edit ∩ relevant / relevant
CWU_window   = peak_context_tokens / window_tokens
```

`CWU_coverage` — заголовочное число. `CWU_window` — контекст: он объясняет,
почему агент не дочитал, и предупреждает о потере ранних инструкций.

**Пороги.**

| CWU_coverage | Статус | Смысл |
|---|---|---|
| `≥70 %` | зелёный | агент видел релевантную картину |
| `40–70 %` | жёлтый | часть связей не проверена |
| `<40 %` | красный | действие вслепую |

`CWU_window >85 %` — отдельная жёлтая метка «риск вытеснения инструкций»,
но не замена coverage.

**Источники.** Лог чтения файлов и tool-call'ов сессии. Если его нет —
`missing`; восстанавливать по «какие файлы открывались» вручную нельзя,
это будет выдумка.

**Матрица интерпретации.** См. `SKILL.md`. Кратко:

- низкий CWU + низкий ADS — слепая удача, проверять связность;
- низкий CWU + высокий ADS — слепое нарушение, лечить контекст;
- высокий CWU + низкий ADS — норма;
- высокий CWU + высокий ADS — агент знал правила и нарушил: архитектурное
  противоречие, нужен ADR и разговор, а не ещё контекст.

**Ловушки.**

- мерить только окно и называть это пониманием;
- включать в `relevant` весь репозиторий — покрытие станет нулевым;
- считать чтение файла пониманием: файл мог быть прочитан после правки;
- сравнивать CWU разных моделей с разными окнами без указания окна.

## Сводка взаимодействий

| Комбинация | Что означает | Первое действие |
|---|---|---|
| высокий FTB + высокий AIR | процесс дорогой и не сходится | разобрать thrash, уменьшить размер задачи |
| высокий CLI + высокий ADS | широкое изменение переопределяет архитектуру | разбить на слои, добавить ADR |
| низкий CWU + высокий HR | агент выдумывал вместо чтения | расширить контекст, включить проверку импортов |
| высокий CWU + высокий FTB | агент читал много и дорого | улучшить навигацию и карту репозитория |
| высокий ADS + высокий CWU | понял правила и нарушил | архитектурное решение, не обучение |

## Минимальный набор для первого отчёта

Если телеметрии пока нет, отчёт всё равно полезен:

- `ADS` — `expert` по чек-листу контракта;
- `CLI` — `derived` из Git/AST;
- `HR` — `derived` по резолвингу импортов и путей;
- `FTB`, `AIR`, `CWU` — `missing` с указанием, какой лог включить.

Это честный снимок «что уже видно», а не повод откладывать отчёт до
появления идеальной телеметрии.
