# dev-pr-report-html — HTML-отчёт об изменениях фичи или майлстоуна

Скилл собирает **один автономный HTML-файл**, который отвечает на вопрос
«что именно произошло с кодом и как работал агент», а не «какие файлы
изменились». Открывается двойным щелчком, без сервера и без сети; печатается
в PDF; прикладывается к PR, демо или записи аудита.

Домен — разработка: в репозитории скилл лежит в `dev/`, имя начинается с
`dev-`. При установке каталог копируется в
`~/.config/opencode/skill/dev-pr-report-html/`.

Нормативные документы:

| Файл | Содержание |
|---|---|
| `references/metrics.md` | Определения, формулы, веса, источники данных, пороги, интерпретация каждой из шести метрик |
| `references/html-contract.md` | Структура страницы, JSON-схема, дизайн-токены, доступность, печать, безопасность |
| `templates/report.html` | Готовый шаблон страницы: стили, графики, интерпретационная матрица |
| `scripts/collect_metrics.py` | Сбор Git/AST-метрик в `metrics.json`; telemetry подмешивается файлом |
| `scripts/build_report.py` | Сборка HTML из `metrics.json` и шаблона |
| `examples/metrics-example.json` | Полный пример данных |
| `examples/telemetry-example.json` | Пример телеметрии: токены, итерации, контекст |
| `examples/example-report.html` | Пример готовой страницы |

> Если `skill` tool не видит скилл, положите каталог в
> `.opencode/skill/dev-pr-report-html/` или
> `~/.config/opencode/skill/dev-pr-report-html/`. До установки читайте
> `SKILL.md` и `references/` напрямую.

## Когда применять

- фича или майлстоун закрыты, нужен отчёт для ревью, руководства или ретро;
- сравниваются два прогона агента на одной задаче;
- нужно объяснить, почему изменение «зелёное по тестам», но дорогое,
  широкое или архитектурно рискованное;
- нужен снимок метрик перед релизом или аудитом фазы.

Не применять: для отчёта о качестве продукта в целом (это `report`),
для презентации (это `pptx-report`), для разбора одного дефекта (это
`bugfix`/`postmortem`). Здесь предмет — **изменение кода и процесс его
получения**.

## Инварианты

1. **Один файл.** CSS, JS, данные и графика внутри; ни одного внешнего
   запроса. Шрифты — системные. Картинки — только встроенные (SVG/data URI).
2. **Каждое число имеет происхождение.** Команда, файл, диапазон коммитов
   или артефакт сессии + дата. Число без источника не попадает на страницу.
3. **Пять уровней качества данных.** `measured` — из телеметрии или
   инструмента; `derived` — вычислено из Git/кода; `estimated` — оценка по
   явной формуле; `expert` — суждение ревьюера по чек-листу; `missing` —
   данных нет. Уровень печатается рядом с числом; `estimated` всегда с
   `~` и диапазоном.
4. **Нет правил — нет ADS.** Architecture Drift считается только против
   явного архитектурного контракта (конституция, ADR, import-linter,
   границы слоёв). Если контракта нет, скилл сначала фиксирует его в отчёте
   как допущение, а нарушения помечает `expert`, а не выдаёт за факт.
5. **Метрика — не приговор человеку.** Отчёт оценивает изменение и процесс,
   а не разработчика. Формулировки — про артефакт: «изменение затронуло
   7 модулей», а не «автор не справился».
6. **Сначала данные, потом вывод.** Числа собираются до текста; вердикт
   пишется после матрицы интерпретации, а не подгоняется под желаемый цвет.

## Быстрый старт

```bash
# 1. Собрать всё, что выводится из Git и кода
python scripts/collect_metrics.py \
  --repo /path/to/repo \
  --from v1.4.0 --to HEAD \
  --out metrics.json

# 2. Добавить телеметрию агента (токены, итерации, контекст)
#    формат — references/metrics.md, раздел «Telemetry»
python scripts/collect_metrics.py --repo /path/to/repo \
  --from v1.4.0 --to HEAD --telemetry telemetry.json --out metrics.json

# 3. Заполнить смысловые поля (summary, drivers, verdict, actions)
#    прямо в metrics.json — схема в references/html-contract.md

# 4. Собрать страницу и открыть
python scripts/build_report.py metrics.json -o feature-report.html --open

# Проверить шаблон без своих данных
python scripts/build_report.py --example -o example-report.html
```

Если телеметрии нет, `collect_metrics.py` пишет `null` и `quality: "missing"`
для FTB/AIR/CWU. Это нормальный результат: страница покажет «нет данных» и
объяснит, как их получить, вместо выдуманного числа.

## Шесть метрик

Порядок секций на странице фиксирован.

| № | Метрика | Что измеряет | Формула (кратко) | Основной источник |
|---|---|---|---|---|
| 1 | 💰 **Feature Token Budget** | полная стоимость изменения в токенах и деньгах | Σ input + output + cache по всем сессиям; на 100 LOC и на сущность | телеметрия провайдера/сессии |
| 2 | 🏗 **Architecture Drift Score** | долю архитектурных решений, нарушивших правила репозитория | `100 × Σ(w·нарушения) / (Σ(w·нарушения) + Σ(w·соблюдено))`, w = 5/3/1 | import graph, ADR, линтеры, diff |
| 3 | 🧠 **Cognitive Load Index** | сколько сущностей и модулей пришлось удержать в голове | Σ весов сущностей + blast radius; нормировка к медиане последних фич | diff, AST, граф зависимостей |
| 4 | 🔄 **Agent Iteration Rate** | сколько циклов и повторов потребовал агент | неудачные проверки / все проверки; циклы на задачу; max повторов одной ошибки | логи инструментов, CI, история коммитов |
| 5 | 👻 **Hallucination Risk** | использованы ли несуществующие API, импорты, файлы | взвешенные подтверждённые случаи на 1000 изменённых LOC | резолвинг импортов, type checker, проверка путей |
| 6 | 📏 **Context Window Utilization** | насколько полно агент использовал контекст репозитория | покрытие релевантных файлов до первой правки; пик окна | лог чтения файлов и tool-call'ов |

Точные определения, веса и пороги — `references/metrics.md`. Ниже — только
то, что нельзя перепутать.

### 1. Feature Token Budget

Считается по всей работе над фичей, включая исследование, провалы и ревью,
а не только по финальному ответу. Разделяйте:

- **input** — промпты, прочитанные файлы, вывод инструментов;
- **output** — сгенерированный код и текст;
- **cache read/write** — если провайдер их различает.

Нормализуйте: `токенов на 100 LOC`, `токенов на изменённую сущность`,
`доля повторных прогонов`. Абсолютное число без нормировки сравнивать
нельзя: фичи разного размера.

### 2. Architecture Drift Score

Сначала найдите контракт. Затем проверьте по нему **решения**, а не строки:

| Класс | Пример | Вес |
|---|---|---|
| critical | новый слой/цикл зависимостей без ADR; домен импортирует инфраструктуру | 5 |
| major | новый публичный API без контракта; миграция без rollback; обход границы модуля | 3 |
| minor | отклонение от соглашения об именовании слоя; дублирование capability | 1 |

`0 %` — все архитектурные решения соблюли правила. `>15 %` — красная зона:
изменение переопределяет архитектуру, а не следует ей. Подробности и
таблица допустимых рёбер — `references/metrics.md`.

### 3. Cognitive Load Index

Считаются **изменённые сущности**, а не строки: модули, пакеты, публичные
функции и классы, таблицы и миграции, маршруты, внешние зависимости,
конфигурационные ключи. Отдельно считается **blast radius** — сколько
модулей зависят от затронутых. Индекс нормируется к медиане последних
фич: `1.0` — типичная нагрузка, `>3.0` — изменение трудно удержать в
голове и ревьюить одним проходом.

### 4. Agent Iteration Rate

Три числа, а не одно:

- **failure rate** = неудачные проверки / все проверки;
- **loops** = циклов «план → правка → проверка» на принятую задачу;
- **thrash** = максимальное число повторов одной и той же падающей команды
  без изменения гипотезы.

`thrash ≥ 3` — красный флаг независимо от среднего: агент не учится на
собственном выводе. Ручные вмешательства считаются отдельно и не
маскируются в общий процент.

### 5. Hallucination Risk

Только **подтверждённые** случаи идут в счёт:

| Тип | Пример | Вес |
|---|---|---|
| phantom API | вызов метода, которого нет в установленной версии | 5 |
| wrong signature | существует, но с другими аргументами | 3 |
| missing import/module | импорт не резолвится в окружении проекта | 2 |
| stale reference | ссылка на несуществующий файл, флаг, команду | 1 |

Сомнительное — в раздел «не подтверждено», не в счёт. Внешний импорт,
которого нет в текущем окружении, но который объявлен зависимостью, — не
галлюцинация; это ограничение проверки, оно пишется явно.

### 6. Context Window Utilization

Две величины, обе нужны:

- **coverage** — какая доля релевантных файлов была прочитана до первой
  правки. Релевантные: затронутые модули, их импортёры, тесты, конвенции и
  ADR. Низкое покрытие = агент действовал вслепую.
- **window** — пиковое заполнение контекстного окна. Высокое значение
  объясняет компромиссы и риск потери ранних инструкций.

Заголовочное число — coverage. `window` — вторая полоса, не замена.

## Матрица интерпретации

Страница строит её автоматически по ADS и CWU. Это главный смысловой блок
отчёта, а не украшение.

| | ADS низкий (<5 %) | ADS высокий (>15 %) |
|---|---|---|
| **CWU низкий (<40 %)** | Слепая удача: малое изменение, но связность не проверена. Смотрите blast radius и тесты. | Слепое нарушение: агент не знал правил. Лечится контекстом: конституция, ADR, карта модулей. |
| **CWU высокий (>70 %)** | Informed compliance: агент знал правила и соблюдал их. Норма. | **Архитектурное противоречие:** агент понял правила и нарушил их. Нужен разговор и ADR, а не ещё контекст. |

Пограничные значения попадают в «серая зона» — так и подписываются, без
натягивания в угол.

## Порядок работы

1. **Зафиксировать рамку.** Что считается изменением: диапазон коммитов,
   ветка, PR или майлстоун. Записать `range`, дату снимка, модель/агента.
2. **Собрать Git-факты.** `collect_metrics.py` → `metrics.json`. Проверить
   предупреждения: пропущенные бинарные файлы, переименования, submodule.
3. **Подмешать телеметрию.** Токены, проверки, чтения файлов. Источник
   каждого поля — в `sources`.
4. **Проверить ADS вручную.** Найти контракт, подтвердить каждое нарушение
   файлом и строкой. Отчёт агента не принимается на веру.
5. **Проверить галлюцинации.** Резолвинг импортов и type checker — в
   окружении проекта, а не в голове. Ложные срабатывания убрать с
   обоснованием.
6. **Написать смысл.** Для каждой секции: `summary` (1–2 предложения),
   `drivers` (что именно дало число), `evidence`, `verdict`, `actions`.
7. **Собрать и проверить страницу.** Открыть в браузере, пройти чек-лист
   ниже, распечатать в PDF и убедиться, что ничего не разъехалось.

## Анатомия страницы

```
Шапка: фича/майлстоун, диапазон, дата, агент, качество данных
Вердикт: 6 KPI-карточек + матрица CWU × ADS
1. 💰 Feature Token Budget      — стоимость, разбивка, нормализация
2. 🏗 Architecture Drift Score  — шкала, нарушения с файлом/строкой
3. 🧠 Cognitive Load Index      — сущности, blast radius, нормировка
4. 🔄 Agent Iteration Rate      — циклы, провалы, thrash, вмешательства
5. 👻 Hallucination Risk        — подтверждённые/неподтверждённые, проверки
6. 📏 Context Window Utilization— coverage, window, что прочитано
Реестр доказательств: утверждение → источник → дата
Решения: что чинить сейчас, что в следующую итерацию, что принять
```

Полная спецификация компонентов — `references/html-contract.md`.

## Правила честности

- Не выдавать оценку за измерение. `~1.8M` и `1 842 310` — разные уровни
  доверия; бейдж обязателен.
- Не считать «стоимость фичи» по одной удачной сессии, если были провалы и
  перезапуски: бюджет включает их.
- Не сравнивать ADS между репозиториями с разными контрактами.
- Не ставить красный статус без порога из `references/metrics.md` или
  явно заданного бюджета. «Мне кажется много» — не порог.
- Не превращать отчёт в оценку сотрудника. Метрики характеризуют изменение
  и процесс, не человека.
- Не публиковать секреты, токены, содержимое `.env`, персональные данные.
  Пути и имена файлов допустимы; значения — нет.
- Если данных нет — писать «нет данных» и как их получить. Пустая секция
  честнее выдуманной.

## QA перед сдачей

- [ ] файл открывается с диска без сети; в DevTools нет внешних запросов;
- [ ] все шесть секций на месте, порядок соблюдён;
- [ ] у каждого числа есть бейдж качества и источник;
- [ ] `estimated` помечено `~` и имеет диапазон;
- [ ] архитектурные нарушения подтверждены файлом и строкой;
- [ ] галлюцинации проверены в окружении проекта, ложные — сняты;
- [ ] матрица CWU × ADS соответствует числам в секциях;
- [ ] вердикт и действия не противоречат данным;
- [ ] нет секретов, токенов и персональных данных;
- [ ] печать в PDF: секции не разрезаны, таблицы не обрезаны, цвета
      различимы в градациях серого;
- [ ] ссылки в реестре доказательств открываются или однозначно называют
      команду.

## Типовые ошибки

- Отчёт о диффе вместо отчёта о работе: списки файлов без метрик и выводов.
- Токены «по одной сессии»: потерянные провалы и повторные прогоны
  занижают бюджет в разы.
- ADS без контракта: нарушения выдуманы, число не значит ничего.
- CLI по строкам кода: 2000 строк в одном модуле — меньшая нагрузка, чем
  200 строк в двенадцати.
- AIR как среднее: три повтора одной ошибки тонут в общем проценте.
- HR по «похоже на выдумку»: без проверки импорта это не метрика.
- CWU только по окну: 95 % окна при 10 % нужных файлов — это слепота, а не
  глубина.
- Красный вердикт без названного порога и без действия.
- Страница с CDN-шрифтами и внешними графиками: при передаче коллеге
  разваливается.
- Оценка людей вместо изменения.
