# Гейты stories и тестов

Нормативный документ `dev-feature-start`. Фиксирует порядок, при котором
разработка начинается с тестов.

## 1. Последовательность

```
ветка → US → B → F → U* → тесты реализованы → RED → задачи → GREEN
```

`U*` — юнит-тесты, если в репозитории есть правило покрытия.

- **US** — user stories с критериями приёмки.
- **B** — поведенческие тесты: что видит пользователь.
- **F** — функциональные тесты: детали, границы, отказы.
- **U** — юнит-тесты, если есть правило покрытия.
- **RED** — тесты реализованы и падают.
- **GREEN** — полный прогон проходит после реализации задач.

## 2. Режим утверждения

| Режим | Кто утверждает | Evidence |
|---|---|---|
| `user` | пользователь | имя, дата, комментарий |
| `autonomous` | агент по заданным критериям | критерии, дата, ссылка на решение пользователя |

Режим выбирает пользователь на старте. В `overview.md` он записан в шапке и
журнале утверждений.

## 3. User stories

Каждая story содержит:

- id `US-*`;
- сценарий пользователя;
- наблюдаемый критерий приёмки;
- статус `draft` / `approved`.

Без утверждённых stories тесты не пишутся.

## 4. Поведенческие тесты

- id `B-*` и ссылка на `US-*`;
- проверяют наблюдаемое поведение, а не внутреннюю реализацию;
- не дублируют функциональные детали;
- статус `draft` / `approved`.

## 5. Функциональные тесты

- id `F-*` и ссылка на `US-*`;
- покрывают детали, границы и отказы;
- могут быть модульными, API или интеграционными;
- статус `draft` / `approved`.

## 5.1 Юнит-тесты

Добавляются, если в репозитории есть правило покрытия:

- `fail_under` в `pyproject.toml`, `setup.cfg`, `.coveragerc` или `tox.ini`;
- `coverageThreshold` в Jest/package.json;
- аналогичное правило в другом конфиге.

Правила:

- id `U-*` и ссылка на `US-*` или модуль;
- проверяют единицу, которую требует покрытие;
- утверждаются до реализации тестов;
- входят в красный и зелёный прогон;
- если правила покрытия нет, в brief фиксируется `not required` и причина.

Юнит-тесты не заменяют поведенческие и функциональные.

## 6. Красный гейт

После реализации тестов:

- команда запуска записана в brief;
- прогон падает;
- в evidence — команда, список падений и дата;
- статус `red`.

Пока гейт не красный, реализация задач не начинается.

## 7. Зелёный гейт

После реализации задач:

- полный прогон, включая регрессии;
- команда и результат записаны;
- статус `green`.

## 8. Изменения после red

Если stories или тесты изменились:

1. вернуть статус в `draft`;
2. утвердить изменения;
3. обновить тесты;
4. повторить красный гейт;
5. только затем продолжить реализацию.

## 9. Антипаттерны

- писать тесты после кода;
- тест, который проходит до реализации;
- поведенческий тест проверяет приватный метод;
- функциональные тесты без привязки к story;
- юнит-тесты только ради процента покрытия;
- «красный» без команды и вывода;
- зелёный только на новых тестах;
- автономное утверждение без критериев и даты.
