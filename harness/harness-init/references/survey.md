# Опрос для bootstrap

Нормативный документ `harness-init`. Опрос проводится до создания файлов и
до выбора маршрута. `harness-init` — единая точка входа: если пользователь
не знает, какой навык нужен, начинать нужно с этого опроса.

## 1. Правила

- Один вопрос — одна тема.
- Нет наводящих формулировок и оценок.
- У каждого вопроса есть значение по умолчанию.
- Ответы сохраняются в `answers.json`, а не теряются в переписке.
- Пользователь может пропустить вопрос; пропуск фиксируется как выбор
  значения по умолчанию.
- Вопросы о научной работе задаются всегда, но при `none` блок считается
  явно пропущенным.
- Вопросы о разработке задаются, если проект предполагает код; при
  `none` SDD не настраивается.

## 2. Блоки опроса

### 2.1 Научные данные и отчёты

| # | Вопрос | Зачем | По умолчанию |
|---|---|---|---|
| 1 | Какую научную работу ведёте: анализ данных, эксперимент, литературный обзор, датасет, визуализация? | выбрать научные навыки | `none` |
| 2 | Какие данные: формат, объём, чувствительность, где хранятся? | проверить воспроизводимость, приватность и лицензии | `не задано` |
| 3 | Какой результат нужен: статья, HTML-отчёт, PPTX, dashboard, датасет? | выбрать `sci-literature-news`, `dev-pr-report-html`, `pptx-report` | `none` |
| 4 | Что нужно для воспроизводимости: код, данные, окружение, лицензия? | зафиксировать артефакты и ограничения | `code` |

Если пользователь выбирает литературный обзор или дайджест, рекомендуется
`sci-literature-news`. Если нужен HTML-отчёт — `dev-pr-report-html`; PPTX
или презентация — `pptx-report`.

### 2.2 Разработка

| # | Вопрос | Зачем | По умолчанию |
|---|---|---|---|
| 5 | Проект новый или существующий: greenfield / brownfield / none? | выбрать маршрут SDD | `none` |
| 6 | Какая специфика: web, ML, CLI, library, критичность, интеграции, deployment? | построить оптимальный workflow и гейты | `не задано` |
| 7 | Нужен ли SDD? | не подменять bootstrap настройкой SDD | `later` |

Если проект предполагает разработку, `harness-init` фиксирует специфику, но
**не настраивает SDD**. Пользователю нужно явно сказать: весь spec-driven
workflow настраивается отдельной командой **`/dev-spec-chain`**. Bootstrap
создаёт базовый профиль, `AGENTS.md`, docs, хуки и CI, а chain стадий —
задача `/dev-spec-chain`.

### 2.3 Библиотека навыков

| # | Вопрос | Зачем | По умолчанию |
|---|---|---|---|
| 8 | Хотите дополнить библиотеку: новый навык, улучшить существующий или нет? | объяснить правильный маршрут | `none` |

Если ответ `new-skill` или `improve-existing`, объяснить порядок:

1. проверить дубли через `harness-skill-audit`;
2. собрать research ledger `docs/research/<skill>.md`;
3. собрать review HTML `docs/reviews/<skill>.html` и получить `approved`;
4. создать навык через `harness-skill-template`;
5. воспроизвести пример и прогнать валидатор;
6. открыть PR со ссылками на research, review и проверки.

Нельзя добавлять навык без research и review. Нельзя дублировать
существующий навык по триггерам.

### 2.4 Общие вопросы

| # | Вопрос | Зачем |
|---|---|---|
| 9 | Какой стек и команды тестов, линтера, сборки? | `profile.yml`, hooks, CI |
| 10 | Какие стартовые задачи: фича, багфикс, релиз, аудит, отчёт, эксперимент? | набор навыков и этапы |
| 11 | Кто работает в репозитории и какие роли нужны? | права и обзоры |
| 12 | Какие ограничения: приватность, безопасность, ревью, CI? | gates и CI |
| 13 | Какие навыки уже есть и какие нужны на старте? | явный выбор |
| 14 | Нужен ли минимальный или расширенный workflow? | объём scaffold |

## 3. Маршруты

| Ответ | Маршрут |
|---|---|
| новый проект или «не знаю, с чего начать» | `harness-init` |
| разработка + SDD | отдельная команда `/dev-spec-chain` |
| новый навык | `harness-skill-template` → research/review → `harness-skill-audit` → PR |
| правило → проверка | `harness-rule-to-mechanism` |
| аудит библиотеки | `harness-skill-audit` |
| настройка обработки дефектов | `dev-bug-processing` |
| научный дайджест | `sci-literature-news` |
| HTML-отчёт | `dev-pr-report-html` |
| презентация | `pptx-report` |

## 4. Соответствие ответов и навыков

| Условие | Рекомендуется |
|---|---|
| всегда | `harness-skill-template`, `harness-skill-audit` |
| задачи `rules`, `quality`, `feature`, `bugfix` | `harness-rule-to-mechanism` |
| задачи `report`, `release`, `audit` или `html-report` | `dev-pr-report-html` |
| задача `presentation` или `pptx` | `pptx-report` |
| научная работа `literature` или результат `literature-digest` | `sci-literature-news` |
| явный список `skills` | используется как есть |

Рекомендуются только **реализованные** навыки. Proposed-навыки попадают в
план как будущие, но не устанавливаются. `/dev-spec-chain` не попадает в
список установленных навыков: это отдельная команда настройки SDD.

## 5. Формат ответов

```json
{
  "project": "example-service",
  "domain": "mixed",
  "stack": "python",
  "default_branch": "main",
  "workflow": "minimal",
  "ci": "github",
  "commands": {
    "test": "pytest -q",
    "lint": "ruff check .",
    "build": ""
  },
  "roles": ["developer", "reviewer"],
  "tasks": ["feature", "bugfix", "literature", "report"],
  "constraints": ["private"],
  "skills": [],
  "science_work": ["literature", "dataset"],
  "science_data": "OpenAlex/DataCite metadata; public",
  "science_outputs": ["html-report", "dataset"],
  "reproducibility": "code, data, env, license",
  "project_mode": "greenfield",
  "dev_specifics": "python, cli, integrations",
  "sdd_setup": "yes",
  "library_contribution": "new-skill"
}
```

Пустой `skills` означает «рекомендовать по ответам». Пустой `science_work`
или `none` означает, что научный блок явно пропущен.

## 6. Утверждение

После опроса собирается `bootstrap-plan.html`:

- профиль научной работы, данных и отчётов;
- специфика разработки и отдельный маршрут SDD;
- решение по пополнению библиотеки;
- стартовые навыки и причины;
- этапы;
- команды;
- список файлов;
- статус `draft` → `approved`.

`apply` не запускается, пока статус не `approved`.

## 7. Ошибки опроса

- спрашивать всё сразу без значений по умолчанию;
- пропускать научные данные и отчёты;
- обещать, что bootstrap настроит SDD вместо `/dev-spec-chain`;
- рекомендовать proposed-навык как готовый;
- скрывать, какие файлы будут созданы;
- добавлять навык в библиотеку без research/review;
- считать молчание согласием;
- начинать scaffold до утверждения.
