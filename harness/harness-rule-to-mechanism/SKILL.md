# harness-rule-to-mechanism — от правила к проверке

Навык превращает договорённость в механизм с владельцем, стоимостью и
доказательством. Правило без механизма считается пожеланием, а механизм без
тест — непроверенным.

Нормативные документы:

| Файл | Содержание |
|---|---|
| `references/mechanism-matrix.md` | выбор механизма по типу правила и моменту проверки |
| `references/registry-format.md` | схема `docs/rules/registry.yml`, поля и жизненный цикл |
| `templates/rule.yml` | карточка одного правила |
| `scripts/validate_rule.py` | проверка registry и evidence |
| `examples/registry-good.yml` | валидный пример registry |
| `examples/registry-bad.yml` | пример с ошибками |

> Если `skill` tool не видит навык, положите каталог в
> `.opencode/skill/harness-rule-to-mechanism/` или
> `~/.config/opencode/skill/harness-rule-to-mechanism/`.

## Когда применять

- правило повторяется на ревью, но нигде не проверяется;
- нужно выбрать между хуком, линтером, тестом и CI;
- в репозитории несколько проверок дублируют друг друга;
- новое правило нужно зарегистрировать с владельцем и стоимостью;
- перед аудитом нужно показать покрытие правил механизмами.

## Когда не применять

- правило ещё не сформулировано — сначала `harness-skill-template` или
  обсуждение;
- нужен аудит всех навыков — это `harness-skill-audit`;
- нужна оценка пользы механизма — это `harness-skill-eval`;
- проверка требует секретов или внешнего сервиса без явного решения.

## Вход

- текст правила и причина, почему оно важно;
- пример нарушения: файл, строка или фрагмент;
- тип правила и ограничения репозитория: язык, CI, допустимый шум;
- владелец правила и допустимый обход.

## Процедура

1. **Классифицировать правило.** Стиль, зависимости, архитектура, конфиг,
   секреты, поведение или процесс.
2. **Выбрать механизм.** Взять самый ранний дешёвый слой из
   `references/mechanism-matrix.md`: editor → hook → test → CI.
3. **Сформулировать if-then.** Записать триггер и действие: «если в
   `domain/` появляется импорт `infrastructure`, проверка падает».
4. **Написать тест.** Тест должен падать на нарушении. Без него механизм
   не считается проверенным.
5. **Реализовать проверку.** Хук, lint-правило, тест, policy-тест или
   CI-шаг. Сообщение должно указывать файл и способ исправления.
6. **Проверить baseline.** На текущем коде проверка не должна шуметь.
7. **Зарегистрировать.** Добавить запись в `docs/rules/registry.yml` по
   `templates/rule.yml`.
8. **Проверить registry.**

   ```bash
   python scripts/validate_rule.py --registry docs/rules/registry.yml --repo .
   ```

9. **Открыть PR.** Приложить карточку правила, тест, вывод
   проверки и строку registry.

## Выход

- карточка правила с id, триггером, механизмом, владельцем и обходом;
- работающий механизм и тест;
- запись в `docs/rules/registry.yml`;
- отчёт `validate_rule.py` с кодом завершения;
- ссылка на PR.

## Доказательства

- тест падает на нарушении;
- baseline проходит без критичных ложных срабатываний;
- `validate_rule.py` завершился кодом `0`;
- в registry у правила есть owner, cost, bypass и evidence;
- механизм воспроизводится без сети, если не указано иное.

## Границы

- Не придумывает правила и не подменяет решение команды.
- Не заменяет ревью, тесты и аудит библиотеки.
- Не добавляет проверку без владельца и разрешённого обхода.
- Не маскирует ложные срабатывания отключением правила.
- Не публикует секреты и внутренние адреса.

## Типовые ошибки

- механизм добавлен, но тест отсутствует;
- проверка шумит на baseline и её отключают;
- правило продублировано в хуке, линтере и CI;
- registry обновлён, а evidence-файл не существует;
- обход `# noqa` добавлен без владельца и срока;
- статус `active` стоит у правила, которое никто не проверяет.

## QA

- [ ] правило классифицировано и сформулировано как if-then;
- [ ] тест падает на нарушении;
- [ ] baseline проходит без критичного шума;
- [ ] механизм выбран по матрице и не дублирует существующий;
- [ ] запись добавлена в `docs/rules/registry.yml`;
- [ ] `validate_rule.py` завершился без ошибок;
- [ ] у правила есть owner, cost, bypass и evidence;
- [ ] ветка запушена и PR открыт.
