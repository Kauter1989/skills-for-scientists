# Матрица «тип правила → механизм»

Нормативный документ `harness-rule-to-mechanism`. Помогает выбрать механизм
до написания проверки.

## 1. Типы правил

| Тип | Пример | Что проверяется |
|---|---|---|
| Стиль | порядок импортов, форматирование, имена | форма кода |
| Зависимости | слой не импортирует слой, нет циклов | граф импортов |
| Архитектура | домен не знает о БД, порты и адаптеры | структура и границы |
| Конфиг | обязательные поля, запрещённые значения | схема конфигурации |
| Секреты | ключи, токены, пароли в коде и истории | строки и файлы |
| Поведение | API возвращает отказ, транзакция откатывается | результат выполнения |
| Процесс | коммит с `main`, PR без ревью, версия без lock | событие или состояние репозитория |
| Данные | миграция без rollback, schema drift | схема и миграции |

## 2. Выбор механизма

| Тип | Первый выбор | Где | Почему |
|---|---|---|---|
| Стиль | formatter / lint | editor + pre-commit | дёшево, мгновенный фидбек |
| Зависимости | import-linter / dependency-cruiser | CI или test | проверяет граф, а не текст |
| Архитектура | architecture test (ArchUnit, import-linter) | test / CI | правило выражается кодом |
| Конфиг | schema validation / Conftest | CI | проверка структурированных данных |
| Секреты | secret scanner (Gitleaks) | pre-commit + CI | специализированный детектор |
| Поведение | unit / integration test | test | проверяет результат |
| Процесс | hook / CI job / branch protection | pre-commit / CI | проверяет событие |
| Данные | migration test / schema check | CI | ловит несовместимость |

Правило выбора:

1. **Самый ранний слой, который ловит нарушение до пользователя.**
2. **Наименьшая стоимость:** секунды локально лучше минут в CI.
3. **Наименьший шум:** проверка не должна требовать ручного разбора
   десятков ложных срабатываний.
4. **Один механизм на правило.** Дублирование допускается только как
   «локально + CI» с разной ролью, а не как две независимые проверки.
5. **Сообщение actionable:** файл, строка, что сделать.

## 3. Слои проверки

| Слой | Плюс | Минус | Когда |
|---|---|---|---|
| Editor | мгновенно | зависит от настройки | стиль и форматирование |
| Pre-commit | до коммита, локально | можно обойти `--no-verify` | быстрые проверки |
| Test | воспроизводимо, в репозитории | требует запуска сюиты | архитектура и поведение |
| CI | нельзя обойти локально | поздний фидбек | обязательные гейты |
| Runtime | ловит реальные условия | дорого, поздно | инварианты и мониторинг |

## 4. Negative fixture

Для каждого правила нужен пример, который **обязан падать**.

- Минимальный: один файл или фрагмент, нарушающий правило.
- Изолированный: не зависит от сети и внешних сервисов.
- Воспроизводимый: команда запуска записана в карточке правила.
- Отдельный от baseline: не ломает обычный прогон.

Без negative fixture правило не переводится в статус `active`.

## 5. Стоимость и шум

Фиксировать в registry:

- **latency** — сколько секунд добавляет проверка;
- **false positives** — сколько ручных разборов на типовой прогон;
- **maintenance** — кто обновляет правило при изменении стека;
- **coverage** — какие файлы или события покрыты.

Ориентиры:

- локальная проверка — до 2 секунд;
- pre-commit — до 10 секунд;
- CI-гейт — до 2 минут;
- больше — выносить в отдельный job или пересматривать правило.

## 6. Обход

Обход допустим только с владельцем и причиной.

- `# noqa` / `allowlist` — точечно, с ссылкой на тикет или ADR;
- глобальное отключение — запрещено;
- обход без срока — запрещён;
- владелец правила проверяет обходы на аудите.

## 7. Антипаттерны

- правило живёт только в документе;
- проверка добавлена, но никто не видел её падения;
- линтер отключён на весь репозиторий;
- архитектурный тест дублирует import-linter;
- pre-commit занимает минуту и его обходят;
- секреты ищут регуляркой в одном файле вместо сканера;
- registry обновлён, но evidence не существует.
