# Severity и политика дублей

Нормативный документ `harness-skill-audit`. Определяет, как классифицировать
находку и что считать блокирующим.

## 1. Шкала

| Severity | Значит | Примеры | Кто решает |
|---|---|---|---|
| `blocker` | Библиотека не выполняет контракт или два навыка неразличимы | точный дубль триггеров; отсутствует `SKILL.md`; сломан обязательный артефакт | пользователь |
| `major` | Навык работает, но контракт нарушен или высок риск ошибки | нет обязательного раздела; пустой `examples/`; битая ссылка; возможный дубль | владелец домена |
| `minor` | Гигиена и долг | legacy без контракта; `TODO`; имя внутреннего проекта | владелец навыка |

`blocker` требует второго прохода: недостаточно машинного совпадения.

## 2. Дубли

Политика по умолчанию: **дублей быть не должно**.

- Точное совпадение `description` — `blocker`.
- Сходство ≥ 0,70 — `major`, возможный дубль.
- Сходство ниже порога — не находка, но может попасть в смысловую выборку.
- Исключение оформляется явно: какие навыки, почему оба нужны и кто
  утвердил.
- Окончательное решение по блокирующему дублю принимает **пользователь**.

Сравнение по словам — эвристика. Она не заменяет чтение сценариев
применения.

## 3. Второй проход

Для каждой blocker-находки:

1. Открыть навык и его триггеры.
2. Сравнить сценарии применения.
3. Записать evidence: файл, строку, цитату.
4. Вынести решение: объединить, развести, оставить исключение.

Без второго прохода находка остаётся `major`, а не `blocker`.

## 4. Отчёт

- HTML: `docs/audits/<date>.html`.
- JSON: `docs/audits/<date>.json`.
- Сортировка: blocker → major → minor.
- Для каждой находки: навык, правило, evidence, рекомендация.
- Секреты, токены и персональные данные в отчёт не попадают.

## 5. Метрики

| Метрика | Что показывает |
|---|---|
| Покрытие структурными проверками | сколько навыков проверено машинно |
| Число blocker/major/minor | текущее состояние |
| Число дублей | риск размывания триггеров |
| Ложные срабатывания | качество правил аудита |
| Согласие второго прохода | надёжность severity |
| Тренд к прошлому аудиту | деградация или улучшение |

## 6. Ошибки аудита

- считать зелёный линтер доказательством качества;
- ставить `blocker` без второго прохода;
- скрывать legacy-навыки вместо отдельного предупреждения;
- сравнивать описания без учёта языка и домена;
- исправлять находки в том же проходе, смешивая аудит и ремонт;
- не сохранять JSON и терять тренд.
