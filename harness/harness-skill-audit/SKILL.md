# harness-skill-audit — аудит библиотеки навыков

Навык проверяет библиотеку целиком или по домену: структуру, дубли
триггеров, артефакты, ссылки и покрытие. Он **read-only** — находит и
фиксирует, но не исправляет.

> **Точка входа.** Если не знаете, с чего начать, — сначала `harness-init`.
> Он проведёт опрос и направит сюда после добавления навыка, перед релизом
> или когда нужен аудит. SDD для нового проекта настраивается отдельно
> командой `/dev-spec-chain`.

Нормативные документы:

| Файл | Содержание |
|---|---|
| `references/audit-checklist.md` | порядок проверки и evidence |
| `references/severity.md` | blocker/major/minor и политика дублей |
| `templates/audit-report.html` | форма отчёта |
| `scripts/audit_library.py` | инвентаризация, проверки, HTML/JSON |

> Если `skill` tool не видит навык, положите каталог в
> `.opencode/skill/harness-skill-audit/` или
> `~/.config/opencode/skill/harness-skill-audit/`.

## Когда применять

- перед релизом или крупным изменением библиотеки;
- после добавления навыка или изменения контракта;
- когда появились жалобы на похожие триггеры;
- нужно сравнить покрытие доменов и тренд находок;
- нужен снимок состояния для ревью.

## Когда не применять

- исправить найденное — это отдельная работа владельца навыка;
- оценить пользу навыка — это `harness-skill-eval`;
- создать правило или механизм — это `harness-rule-to-mechanism`;
- проверить только один навык по контракту — достаточно
  `harness-skill-template`.

## Вход

- корень библиотеки или отдельный домен;
- прошлый отчёт для тренда, если есть;
- политика severity и решение по дублям;
- список навыков, которые нужно проверить углублённо.

## Процедура

1. **Зафиксировать рамку.** Домен, навык или вся библиотека; дата снимка.
2. **Инвентаризировать.** Собрать навыки, домены, контракт и артефакты.
3. **Запустить машинные проверки.**

   ```bash
   python scripts/audit_library.py --root /path/to/skills
   python scripts/audit_library.py --root /path/to/skills --domain harness
   ```

4. **Разобрать дубли.** Точное совпадение — `blocker`; сходство ≥ 0,70 —
   `major`; решение по блокирующему дублю принимает пользователь.
5. **Проверить покрытие.** Пустой домен — повод для решения, а не
   автоматический дефект.
6. **Сделать смысловую выборку.** Новые, недавно изменённые и спорные
   навыки; для `blocker` — второй проход.
7. **Сохранить отчёт.**

   ```bash
   python scripts/audit_library.py --root /path/to/skills \
     --out docs/audits/2026-10-31.html \
     --json-out docs/audits/2026-10-31.json
   ```

8. **Передать находки владельцам.** Исправления идут отдельным PR.

## Выход

- `docs/audits/<date>.html` — отчёт для чтения;
- `docs/audits/<date>.json` — снимок для тренда;
- список находок с severity, evidence и рекомендацией;
- решение по дублям и исключениям.

## Доказательства

- аудит находит заранее внесённые дефекты: дубль, пустой пример, битую
  ссылку;
- повторный запуск на том же снимке даёт тот же результат;
- `blocker` подтверждён вторым проходом;
- HTML открывается без сети, JSON соответствует отчёту;
- число находок и покрытие совпадают с JSON.

## Границы

- Не исправляет навыки и не меняет registry.
- Не оценивает пользу и качество процедуры — это `harness-skill-eval`.
- Не заменяет ревью и не утверждает исключения за пользователя.
- Не ходит в сеть по умолчанию: проверяются локальные ссылки.
- Не скрывает legacy-навыки: фиксирует их отдельным предупреждением.

## Типовые ошибки

- считать зелёный линтер доказательством качества;
- ставить `blocker` без второго прохода;
- сравнивать описания без учёта домена и языка;
- исправлять находки в том же проходе;
- терять JSON и не иметь тренда;
- писать отчёт без evidence и владельца.

## QA

- [ ] рамка аудита и дата зафиксированы;
- [ ] машинные проверки прошли;
- [ ] дубли разобраны, решение по blocker записано;
- [ ] покрытие доменов отражено;
- [ ] `blocker` подтверждён вторым проходом;
- [ ] HTML и JSON сохранены в `docs/audits/`;
- [ ] находки переданы владельцам;
- [ ] секретов и персональных данных нет.
