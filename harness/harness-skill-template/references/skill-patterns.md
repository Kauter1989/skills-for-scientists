# Примеры формулировок

Справочник для автора навыка. Показывает, как выглядит контракт в тексте,
а не только в правилах.

## 1. Описание

### Плохо

```yaml
description: Инструмент для отчётов.
```

Почему: не ясно, что именно делает, когда включать и чем отличается от
соседних навыков.

### Плохо

```yaml
description: >-
  Сначала читает git, потом строит AST, считает метрики, проверяет импорты,
  собирает HTML, пишет рекомендации.
```

Почему: перечислены шаги, а не условие применения. Модель не поймёт, когда
навык нужен.

### Хорошо

```yaml
description: >-
  HTML-отчёт об изменениях фичи или майлстоуна: метрики, доказательства и
  решения. Use when closing a feature or milestone and a review needs numbers
  instead of a diff. Trigger on: отчёт по фиче, milestone report, change report.
```

Почему: есть действие, результат, условие и ключевые слова для поиска.

## 2. «Когда применять»

Плохо:

```markdown
## Когда применять

Всегда, когда нужно.
```

Хорошо:

```markdown
## Когда применять

- закрыта фича или майлстоун, нужен отчёт для ревью;
- сравниваются два прогона агента на одной задаче;
- изменение зелёное по тестам, но дорогое или широкое.
```

## 3. «Когда не применять»

Этот раздел защищает от дублей и неверного вызова.

```markdown
## Когда не применять

- для презентации — есть `pptx-report`;
- для разбора одного дефекта — есть `dev-postmortem`;
- для аудита всей библиотеки — есть `harness-skill-audit`.
```

## 4. Вход и выход

Плохо: «на вход подаётся информация, на выходе результат».

Хорошо:

```markdown
## Вход

- диапазон коммитов `from..to`;
- файл телеметрии с токенами и итерациями;
- архитектурный контракт или ссылка на ADR.

## Выход

- `metrics.json` по схеме `references/schema.md`;
- автономный `report.html`;
- список решений с приоритетом.
```

## 5. Доказательства

Раздел отвечает на вопрос «почему этому результату можно верить».

```markdown
## Доказательства

- валидатор завершился кодом 0;
- пример из `examples/` воспроизведён командой из раздела «Процедура»;
- в HTML нет внешних запросов, консоль браузера без ошибок;
- ссылки на источники открываются и содержат дату обращения.
```

## 6. Границы

```markdown
## Границы

- не выбирает архитектуру за автора;
- не заменяет тесты и ревью;
- не проверяет внешние импорты, если окружение недоступно;
- не публикует секреты и персональные данные.
```

## 7. Типовые ошибки

```markdown
## Типовые ошибки

- запуск на шаблоне вместо созданного навыка;
- пустой `examples/`;
- описание без условия применения;
- ссылка на `references/...`, которого нет;
- вывод «всё хорошо» без команды проверки.
```

## 8. QA

```markdown
## QA

- [ ] имя совпадает с каталогом;
- [ ] описание короче 1024 символов;
- [ ] обязательные разделы на месте;
- [ ] пример воспроизводится;
- [ ] нет `TODO`, секретов и внутренних имён.
```

## 9. Доменные акценты

| Домен | Что добавить |
|---|---|
| `dev` | ветка, тесты, CI, откат, влияние на пользователя |
| `sci` | гипотеза, данные, статистика, ограничения, воспроизводимость |
| `harness` | правила, проверки, стоимость, влияние на другие навыки |
| `reports` | аудитория, источники, дата снимка, формат артефакта |

## 10. Мини-пример целиком

```markdown
---
name: harness-example
description: >-
  Проверяет, что навык следует контракту библиотеки. Use when adding or
  reviewing a skill. Trigger on: проверить навык, skill contract.
license: Apache-2.0
metadata:
  domain: harness
  contract: harness-skill-template
  version: "0.1.0"
---

# harness-example

## Когда применять

- нужно проверить структуру нового навыка.

## Когда не применять

- нужна оценка пользы навыка.

## Вход

- путь к каталогу навыка.

## Процедура

1. Запустить валидатор.
2. Разобрать ошибки.

## Выход

- отчёт валидатора.

## Доказательства

- код завершения 0.

## Границы

- не проверяет смысл.

## Типовые ошибки

- запуск без `--root`.

## QA

- [ ] отчёт прочитан.
```
