# harness-skill-template — контракт и каркас нового навыка

Навык задаёт форму остальным: создаёт каталог, заполняет `SKILL.md` по
контракту и проверяет структуру до ревью. Он не пишет содержание за автора
и не заменяет `harness-skill-audit`.

> **Точка входа.** Если не знаете, с чего начать, или нужен новый проект,
> научная работа либо набор навыков — сначала `harness-init`. Он проведёт
> опрос и направит сюда, только если действительно нужен новый навык.
> SDD для нового проекта настраивается отдельно командой `/dev-spec-chain`.

Нормативные документы:

| Файл | Содержание |
|---|---|
| `references/skill-contract.md` | структура, frontmatter, обязательные разделы, правила имён |
| `references/skill-patterns.md` | хорошие и плохие примеры описаний и разделов |
| `templates/SKILL.md` | каркас для нового навыка |
| `scripts/new_skill.py` | создание каталога и `SKILL.md` |
| `scripts/validate_skill.py` | проверка контракта, ссылок, примеров и скриптов |

> Если `skill` tool не видит навык, положите каталог в
> `.opencode/skill/harness-skill-template/` или
> `~/.config/opencode/skill/harness-skill-template/`.

## Когда применять

- добавляется новый навык в `dev/`, `sci/`, `harness/` или `reports/`;
- существующий навык нужно привести к общему контракту;
- перед ревью нужно проверить структуру, ссылки и примеры;
- нужно объяснить автору, какие разделы обязательны и почему.

## Когда не применять

- для аудита всей библиотеки — это `harness-skill-audit`;
- для оценки эффективности навыка — это `harness-skill-eval`;
- для правки содержания конкретного навыка без изменения структуры;
- для навыков, которые уже объявили другой контракт и проходят его проверку.

## Вход

- домен: `dev`, `sci`, `harness` или `reports`;
- имя навыка в нижнем регистре через дефис, с префиксом домена;
- одно-два предложения: что делает навык и когда его применять;
- пример входа и ожидаемого выхода.

## Процедура

1. **Выбрать домен и имя.** Для `dev`, `sci`, `harness` имя начинается с
   `dev-`, `sci-`, `harness-`. Для `reports` префикс не добавляется.
2. **Создать каркас.**

   ```bash
   python scripts/new_skill.py harness/harness-example \
     --root /path/to/skills \
     --title "Пример навыка" \
     --description "Что делает навык. Use when ..."
   ```

3. **Заполнить `SKILL.md`.** Заменить подсказки в разделах, описать вход,
   процедуру, выход, доказательства и границы. Не оставлять угловые
   скобки и незаполненные заглушки.
4. **Добавить артефакты.** `references/` — нормативы и формулы;
   `scripts/` — детерминированная проверка; `templates/` — форма
   результата; `examples/` — хотя бы один пример входа и выхода.
5. **Проверить.**

   ```bash
   python scripts/validate_skill.py harness/harness-example --root /path/to/skills
   python scripts/validate_skill.py --all --root /path/to/skills
   ```

6. **Передать на ревью.** Для нового навыка обязательны research ledger и
   HTML-ревью со статусом `approved` по `AGENTS.md`.
7. **Открыть PR.** Запушить ветку и открыть pull request с ссылками на
   research, review и вывод валидатора. Мерж без PR запрещён.

## Выход

- каталог навыка с `SKILL.md` и нужными подкаталогами;
- отчёт валидатора: ошибки, предупреждения, пропущенные разделы;
- список следующих шагов: что заполнить и что проверить.

## Доказательства

Валидатор печатает проверки и завершает работу кодом `1` при ошибках.
В отчёте должны быть видны:

- совпадение `name` и имени каталога;
- длина и наличие триггеров в `description`;
- наличие обязательных разделов;
- существование относительных ссылок;
- непустой `examples/`;
- компиляция Python-скриптов.

## Границы

- Не пишет содержательную часть навыка и не придумывает источники.
- Не проверяет смысл и качество процедуры — это ревью и
  `harness-skill-audit`.
- Не заменяет `harness-skill-eval`: структура не доказывает пользу.
- Не устанавливает навык в OpenCode и не меняет глобальные настройки.
- Не проверяет навыки без маркера контракта в `--all`; legacy-навыки
  пропускаются с предупреждением.

## Типовые ошибки

- имя в frontmatter не совпадает с каталогом;
- описание перечисляет возможности, но не говорит, когда навык применять;
- разделы «Границы» и «Доказательства» пустые;
- ссылка на `references/...` ведёт в несуществующий файл;
- `examples/` пуст или содержит только `.gitkeep`;
- в примерах остаются имена внутренних репозиториев и секреты;
- валидатор запускают на шаблоне, а не на созданном навыке.

## QA

- [ ] `name` совпадает с каталогом и проходит regex;
- [ ] `description` короче 1024 символов и содержит условие применения;
- [ ] все обязательные разделы на месте;
- [ ] относительные ссылки существуют;
- [ ] `examples/` не пуст;
- [ ] Python-скрипты компилируются;
- [ ] нет проектных имён, секретов и незаполненных заглушек;
- [ ] для нового навыка собраны research ledger и review HTML;
- [ ] ветка запушена и PR открыт.
