## 1. Задача

Начинать фичу одинаково: ветка от свежей основной ветки, привязка к цели
или пункту плана, краткий feature brief с границами и критериями приёмки,
передача в цепочку спецификации.

**Не входит в задачу:** писать `spec.md`, `plan.md` и задачи (это
spec-chain), реализовывать код, делать commit, push или merge.

## 5. Синтез

- **Повторяющиеся паттерны:** ветка от свежей основы, явная цель, brief,
  критерии приёмки и передача в спецификацию.
- **Противоречия:** тяжёлые branch-модели дают порядок, но дороги для
  маленьких команд; лёгкий feature-branch проще, но требует дисциплины.
- **Пробелы:** инструменты создают ветку, но не связывают её с планом,
  критериями и границами.
- **Что подтверждено эмпирически:** раннее обнаружение дефектов дешевле;
  риск-ориентированный старт фиксирует цели и ограничения; if-then
  формулировка повышает следование плану.
- **Что является решением автора:** формат feature brief, обязательные
  поля и минимальный набор проверок.

## 6. Выводы для дизайна

| Решение | Основание | Альтернатива | Почему не она |
|---|---|---|---|
| Ветка от свежей основной, чистое дерево | git-town; GitHub flow | ветка от локальной main | устаревшая база и конфликты |
| Feature brief до спецификации | Boehm; superpowers | сразу писать spec | нет цели и границ |
| Обязательная ссылка на пункт плана | Boehm; практика | «просто фича» | работа вне плана без обоснования |
| If-then критерий приёмки | Gollwitzer | общее описание | нельзя проверить |
| User stories утверждаются до тестов | Boehm; Gollwitzer | писать тесты по догадке | неясно, что проверяется |
| Поведенческие тесты утверждаются отдельно | Rafique; практика | сразу функциональные тесты | смешиваются сценарий и деталь |
| Тесты реализуются до кода | Rafique | код, потом тесты | тесты подгоняются под реализацию |
| Красный гейт до задач | Rafique; Boehm | «тесты есть» | нет доказательства, что они проверяют |
| Зелёный гейт — полный прогон | практика | только новые тесты | регрессии остаются незамеченными |
| Режим утверждения: user или autonomous | решение пользователя | всегда автономно | нет контроля качества stories |
| `start_feature.py --dry-run` | git-town | ручные команды | забытые шаги |
| Не делать commit/push | практика | полный автомат | скрытые side effects |

## 7. Обязательные гейты overview.md

1. **User stories утверждены.** Список `US-*` с критериями приёмки;
   режим `user` или `autonomous` зафиксирован в brief.
2. **Поведенческие тесты утверждены.** Тесты `B-*` привязаны к `US-*`,
   описывают наблюдаемое поведение, а не реализацию.
3. **Функциональные тесты утверждены.** Тесты `F-*` покрывают детали
   сценариев и граничные случаи.
4. **Тесты реализуются первыми.** После их написания прогон обязан быть
   **красным**; вывод и список падений фиксируются в brief.
5. **Только после красного гейта** начинается реализация задач.
6. **Зелёный гейт:** полный прогон тестов, включая регрессии, проходит.

Режим утверждения:

| Режим | Кто утверждает stories и тесты | Что фиксируется |
|---|---|---|
| `user` | пользователь | имя, дата, комментарий |
| `autonomous` | агент по заранее заданным критериям | критерии, дата, ссылка на решение пользователя |

## 8. Открытые вопросы для ревью

1. Режим по умолчанию: `user` или `autonomous`?
2. Где хранить evidence красного гейта: в `overview.md` или отдельным логом?
3. Красный гейт — только новые тесты или полный прогон?
4. Что делать, если stories изменились после красного гейта?
5. Кто утверждает тесты в автономном режиме?
