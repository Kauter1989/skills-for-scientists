01

Проблема и границы

Дефекты обрабатывают по-разному: в одном репозитории есть pytest и GitHub Issues, в другом — Docker Compose, Jira и production-инциденты, в третьем — пакет исследовательских багов. Один фиксированный процесс либо слишком тяжёл, либо не покрывает окружение. При этом у всех случаев одинаковое ядро: дефект нужно описать, воспроизвести, уменьшить, превратить в падающий тест и только потом искать причину.

Навык решает это как мета-навык: опрашивает репозиторий, выбирает подход и генерирует операционный навык. Ядро не настраивается, церемония и инструменты — настраиваются.

Входит в задачу

  • опрос: стек, тесты, трекер, окружение, команда;
  • выбор подхода по профилю;
  • HTML-план и approved до генерации;
  • генерация dev-bug-process в целевом репозитории;
  • манифест с командами, путями и гейтами;
  • проверка структуры и инвариантов.

Не входит

  • обрабатывать конкретный дефект за сгенерированный навык;
  • исправлять код и закрывать регрессии;
  • проверять живой стенд и деплой;
  • ставить новую фичу — dev-feature-start;
  • генерировать цепочку спецификаций — dev-spec-chain;
  • оценивать людей и автора отчёта.

04

Синтез и предлагаемый дизайн

Мета-слой даёт опрос и генерацию артефактов, прикладной слой — проверяемое воспроизведение. Навык соединяет их: профиль репозитория выбирает команды, пути и инструменты, но не отключает гейты. Это закрывает пробел между генераторами спецификаций и инструментами отладки.

1. Survey→ 2. Profile→ 3. Approach→ 4. HTML plan→ 5. approved→ 6. Generate→ 7. Check

Матрица подходов

ПрофильПодходЧто добавляет
Локальный тестовый фреймворк, обычные дефектыtest-firstred test, минимальный вход, bisect
Зависимость от окружения или сервисовcontainer-firstзакреплённый образ, compose, детерминированные данные
Production-инцидентincident-firsttimeline, логи и трейсы, rollback, затем локальное воспроизведение
Много дефектов или исследовательский стендbenchmark-firstпакетная обработка, метаданные, сравнение ревизий
Малая команда, простой процессlightweightминимальный отчёт без тяжёлого трекера

Инварианты, которые не отключаются

#ИнвариантПроверка
I1Подробное описание: expected/actual, окружение, версия, шаги, входы, логиполя repro.json
I2Воспроизводимость: ≥3 прогона с одинаковым результатомprobe.json
I3Минимальный вход, каждый остаток обоснованminimal_case, removed
I4Падающий автотест до фиксапуть, имя, red output
I5Падение соответствует symptomfailure_matches_symptom
I6Диагноз: гипотезы с evidence, confidence и следующим probehypotheses[]
I7Нет фикса до красного гейтастатус и порядок шагов
I8Артефакты в docs/bugs/<id>/манифест и файлы
I9Недоверенные команды не запускаются автоматическиявное решение пользователя

Вход

  • репозиторий или его профиль;
  • стек и тестовый фреймворк;
  • команда тестов и путь к тестам;
  • трекер и формат issue;
  • окружение: local / container / production;
  • команда, compliance, flake policy;
  • режим утверждения user / autonomous.

Выход

  • bug-processing-plan.html и JSON;
  • .opencode/bug-processing.yml;
  • .opencode/skill/dev-bug-process/SKILL.md;
  • references, templates и scripts навыка;
  • docs/bugs/<id>/ — шаблон артефактов;
  • отчёт check_bug_skill.py.

Артефакты мета-навыка

  • SKILL.md — опрос, выбор подхода, генерация, границы;
  • references/approach-selection.md — профили и матрица;
  • references/bug-contract.md — инварианты, поля, статусы, confidence;
  • templates/bug-processing-plan.html — план на утверждение;
  • templates/bug-processing.yml — манифест;
  • templates/generated-SKILL.md — шаблон dev-bug-process;
  • scripts/generate_bug_skill.py — survey / plan / approve / apply;
  • scripts/check_bug_skill.py — проверка сгенерированного навыка;
  • examples/answers-python.json, answers-container.json, готовый план.

Метрики и план проверки

Генерация — 3 профиля → 3 подхода Инварианты — 9/9 в манифесте Проверка — exit 0 на примере Отказ — apply до approved → exit 2
  1. generate_bug_skill.py plan на python-профиле: ожидается test-first и 5 стадий.
  2. plan на container-профиле: ожидается container-first и блок окружения.
  3. apply до approve: ожидается отказ.
  4. apply после approve: созданы манифест и dev-bug-process/SKILL.md.
  5. check_bug_skill.py --root: exit 0; при удалённом инварианте — exit 1.
  6. --dry-run: ничего не пишет.

Вопросы к ревьюеру

  1. Имя сгенерированного навыка: dev-bug-process или dev-bug-processing? Предлагается process, чтобы не конфликтовать с мета-навыком.
  2. Минимум 3 прогона достаточно? Предлагается 3 обязательных, 5 для флейков.
  3. Фикс при estimated или только при derived/measured? Предлагается derived.
  4. Incident-first: mitigation до red разрешать? Предлагается да, фикс — нет.
  5. Генерировать шаблон issue для GitHub/Jira? Предлагается опционально.
  6. Нужен ли git bisect в сгенерированном навыке? Предлагается только команда, без автозапуска.
