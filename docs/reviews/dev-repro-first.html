dev-repro-first

Дефект → стабильное воспроизведение → минимальный вход → падающий автотест → журнал гипотез с evidence. До начала исправления.

Домен: dev Приоритет: P0 Автор: OpenCode agent Дата: 2026-11-01 Источники: 17 draft
Запрос решения

Утвердить навык, который до фикса выдаёт три проверяемых артефакта: детерминированный reproducer, падающий тест, привязанный к symptom, и диагноз с ранжированными гипотезами и evidence. Утверждаются гейты, формат repro.json и скрипты probe_repro.py / check_repro.py.

01

Проблема и границы

Дефект часто начинают чинить по описанию: причина угадывается, тест пишется после фикса и проверяет реализацию, а «иногда падает» принимается за воспроизведение. В результате фикс не подтверждён, а регрессия возвращается. Нужен короткий процесс, который сначала делает дефект наблюдаемым и проверяемым.

Входит в задачу

  • сформулировать expected / actual и окружение;
  • добиться детерминированного падения и измерить его;
  • уменьшить вход, сохранив падение;
  • превратить reproducer в падающий автотест;
  • проверить, что падение соответствует symptom;
  • ранжировать гипотезы причины с evidence и confidence.

Не входит

  • исправление кода — это следующий шаг;
  • закрытие регрессий после фикса — dev-regression-guard;
  • проверка на живом стенде — dev-verification-live;
  • постановка новой фичи — dev-feature-start;
  • оценка людей и «качества» автора отчёта;
  • автоматический поиск всех причин без проверки.

04

Синтез и предлагаемый дизайн

Аналоги дают три разных механизма: shrinking (Hypothesis, fast-check), детерминированный reproducer (OSS-Fuzz, Defects4J) и ранжирование подозрительных мест (GZoltar). Ни один не покрывает процесс целиком. Навык соединяет их в один гейтовый проход и добавляет то, чего нет в инструментах: проверку, что красный тест падает именно из-за заявленного symptom.

1. Intake→ 2. Reproduce ×3→ 3. Minimize→ 4. Red test→ 5. Diagnose

Вход

  • отчёт о дефекте или наблюдение;
  • ожидаемое и фактическое поведение;
  • версия, коммит, ОС, зависимости;
  • шаги, входные данные, логи;
  • команда запуска и тестовый фреймворк.

Выход

  • docs/bugs/<slug>/repro.md;
  • repro.json — машиночитаемый отчёт;
  • probe.json — результат 3–5 прогонов;
  • падающий тест в обычном тестовом дереве;
  • ранжированные гипотезы с evidence;
  • решение reproduced / not-reproduced / flaky.

Гейты до фикса

ГейтПроверкаEvidence
G1. Falsifiableexpected и actual сформулированы так, что их можно проверитьполя в repro.json
G2. Deterministicминимум 3 прогона, все падают одинаково; иначе flakyprobe.json
G3. Minimalвход уменьшен; каждый оставшийся элемент обоснованminimal_case и removed
G4. Right failureсообщение и стек соответствуют symptom, а не ошибке setupfailure_matches_symptom: true
G5. Red testавтотест существует и падает на текущей ревизиипуть, имя и red output
G6. Diagnosisу каждой гипотезы есть evidence, confidence и следующий probehypotheses[]

Артефакты навыка

  • SKILL.md — триггеры, процедура, гейты, границы;
  • references/repro-contract.md — поля, статусы, confidence, минимальность;
  • references/fault-localization.md — bisect, delta debugging, SBFL, правила вывода;
  • scripts/probe_repro.py — N прогонов команды, классификация и probe.json;
  • scripts/check_repro.py — проверка полноты и согласованности repro.json;
  • templates/repro.md, templates/repro.json — форма отчёта;
  • examples/mini-project/ — намеренно падающий тест и заполненный отчёт.

06

Метрики и план проверки

Полнота отчёта — 0 ошибок check_repro.py Детерминированность — 3/3 одинаковых падения Минимальность — каждый остаток обоснован Диагноз — ≥1 гипотеза с evidence
  1. Собрать пример с дефектом и запустить probe_repro.py --runs 3 -- python -m unittest ...: ожидается deterministic-fail, 3/3.
  2. Запустить check_repro.py --report docs/bugs/<slug>/repro.json --strict: ожидается exit 0.
  3. Проверить отрицательные случаи: без теста, с 1 прогоном, с несовпадением symptom, без гипотез — каждый даёт exit 1 и точную ошибку.
  4. Проверить, что пример не ломает остальные тесты библиотеки и запускается только явной командой.

Вопросы к ревьюеру

  1. Падающий тест хранить в обычном тестовом дереве, а docs/bugs/<slug>/ — только для отчёта? Предлагается да.
  2. Минимум 3 прогона достаточно? Предлагается 3 обязательных, 5 рекомендуемых для флейков.
  3. Фикс разрешать при estimated или только при derived/measured? Предлагается derived, иначе нужно явное решение пользователя.
  4. Нужен ли отдельный repro.sh или команды в repro.json достаточно? Предлагается команда в JSON, скрипт — опционально.
  5. Невоспроизведённый дефект закрывать как not-reproduced с планом или оставлять investigating? Предлагается not-reproduced + следующий probe.
  6. Автоматически запускать git bisect? Предлагается нет: только предложить команду, запуск — по решению пользователя.
